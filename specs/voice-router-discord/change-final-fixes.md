1. Decision 1 (P23/P30, also resolves P28/P29) — tasks outlive their conversation and are reported later:
   - When a session ends, its open tasks stay tracked by the service-wide TaskTracker as "unattended" (rename/replace the current "unfollowed" concept; keep run ids, person, profile).
   - On service start, load tasks that were still open (queued/running with a run id) from $HERMES_HOME/duplex/tasks.jsonl into the tracker as unattended, so a restart does not lose them.
   - When a person starts a new conversation (any transport), the session adopts that person's unattended tasks: resumes following each run (HermesApiClient.events with resubscribe/poll fallback, as for live tasks); runs that already ended are fetched via GET status. Results that finished while the person was away are announced through the normal announcement queue, prefixed by a notice like "While you were away, task N finished: …" (add to notices.py); failures/cancels likewise as notices.
   - Unattended tasks count again for ahead_of (correct "queued behind"), task_status (status by number and summaries; say "running, I'll tell you when it finishes" etc.) and cancel (by number or as the latest).
   - Queued-without-run-id tasks still expire to unknown as today.
   - Service stop leaves runs running in Hermes (persisted state lets the next start pick them up). Update architecture.md, README known limitations (remove the "runs left running / not cancellable" limitation), and the master plan amendment note is handled by the orchestrator.
   - Tests: session end → new session for same person announces a result that completed meanwhile; status/cancel of an adopted task; restart path (tracker loads open tasks from jsonl); ahead_of counts unattended tasks; other people's tasks are not adopted.
